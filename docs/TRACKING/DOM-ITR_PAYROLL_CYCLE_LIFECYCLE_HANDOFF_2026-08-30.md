## 1. What This Work Is

The Interpretation Domain (`DOM-ITR-001`) migration. The just-completed slice was **documentation-only** and establishes a **payroll-cycle-boundary lifecycle**:

- **Payroll completion IS the economic-cycle boundary event.** When a class-level payroll run closes cycle N, that is the lawful boundary that drives Interpretation to compute + materialize.
- Coordination is via a **canonical FEAT (`FEAT-PROD-004`)**, never direct domain-to-domain calls (`INV-ARC-021` §V.2).
- Interpretation persistence is a **durable, immutable, cycle-bound** record (`interpretation_cycle_record`) that stores the actual economic reference values consumed, so a closed cycle is self-describing and never reinterpreted.

This replaces the retired `interpretation_snapshots` / `interpretation_annotations` tables and the retired Behavioral/Structural axis model.

## 3. The Lifecycle (FEAT-PROD-004 ordering)

At payroll cycle completion, `FEAT-PROD-004` orchestrates, in one atomic, fail-closed, idempotent transaction:

1. **Open the new cycle** — generate a fresh `payroll_cycle_id` (UUID).
2. **Settle the closing cycle** — per-seat payroll settlement via `FEAT-PROD-003` (`record_payroll_event` stamps the run's `payroll_cycle_id` onto each `payroll` row; it does NOT generate the id or orchestrate side effects).
3. **Materialize interpretation** — invoke `FEAT-ITR-001` to compute the closed cycle's Interpretation and write **exactly one** immutable `interpretation_cycle_record` bound to `(class_id, payroll_cycle_id)`.
4. **Activate pending next-cycle policy** — apply any `pending` `next_boundary` policy transition as a lawful append-only `applied` transition (`DOM-CLASS-003`).
5. **Commit.**

Interpretation NEVER decides on its own that a cycle is "ready" to materialize — materialization is only a declared side effect of `FEAT-PROD-004`.

## 4. Three Distinct Identities (never conflate)

- **`payroll_cycle_id`** — durable economic-period UUID. Generated by the completion command (`FEAT-PROD-004`). Groups all `payroll` events of one cycle. The economic-cycle identity.
- **`correlation_id`** — per-seat event/obligation lineage.
- **`idempotency_key`** — command replay guard.

## 5. `interpretation_cycle_record` (DOM-ITR-001 §IX)

Durable, immutable, self-describing, cycle-bound. **Not a cache.** Append-only; never updated or recomputed.

Columns:
- `id` UUID PK
- `class_id` UUID (shared anchor)
- `payroll_cycle_id` UUID (economic-cycle identity from FEAT-PROD-004; one record per `(class_id, payroll_cycle_id)`)
- `cycle_started_at`, `cycle_completed_at`, `computed_at` TIMESTAMPTZ (UTC)
- `reference_configuration` **JSONB** — versioned immutable informational projection of consumed config (see below)
- `observations_json` JSONB — materialized Descriptive observations + Interpretive signals, each carrying §IV output-property declarations

### `reference_configuration` contract (the key design decision)

Versioned JSONB, conceptual shape:
```json
{
  "schema_version": 1,
  "economic_engine": { "cwi": "...", "expected_weekly_hours": "...", "hourly_pay_rate": "..." },
  "policy": { "policy_uuid": "...", "version": "..." }
}
```
It is:
- an **immutable informational projection** of the config actually consumed while interpreting the cycle,
- **NOT executable CLASS state** (CLASS / `SPEC-ECON-003` remain sole authority over live config),
- **NOT something ITR may resolve, refresh, or recompute** — frozen with the cycle,
- **versioned** (`schema_version`) so the Economic Engine can evolve without schema churn and old interpretations stay self-describing,
- **NOT an FK** — `policy.policy_uuid` / `policy.version` are informational lineage only.

Rationale: prevents schema churn as the Economic Engine evolves; makes old interpretations self-contained.

**Cross-domain FK rule (`INV-ARC-021` §V.7):** only legal cross-domain FK targets are shared anchors (`class_id`, `seat_id`, `user_id`). No `engine_version_id`, no `policy_versions.id`.

## 7. Doctrinal Contract Corrections Made This Slice (don't regress these)

- `reference_configuration` is versioned JSONB, **not** individual typed columns.
- **INV-ITR-011** is scoped to optional ephemeral read caches ONLY — it can never be read to require rewriting a completed cycle record.
- A completed `interpretation_cycle_record` is **never recomputed**. Reversals/late data affect the cycle in which they occur, not by rewriting history (§X items 1–2, §VII).
- **Pre-contract cycles are explicitly NOT reinterpreted or replayable** — they do NOT become replayable merely because the new table exists. No "backfill" implication anywhere.
- `Materialize` is SPECIFIED (cycle-bound), not built. `Invalidate Snapshot` is NOT APPLICABLE to cycle records.

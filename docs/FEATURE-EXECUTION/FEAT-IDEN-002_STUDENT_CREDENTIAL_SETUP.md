## I. Purpose

This FEAT activates login credentials on a student `User` that was previously provisioned (but not yet authenticated) by **FEAT-IDEN-001** (Unauthenticated Student Seat Claim). It completes the student's onboarding by establishing their username, PIN, and passphrase.

Per DOM-IDEN-002 §VI:
> "A `users` row may be provisioned before claim; credentials are activated when a student claims a seat and completes setup."

This FEAT performs the credential activation step.

**Governing Authority:**
- DOM-IDEN-002 §VI & §VIII.IV (Student Identity Layers and Claim Flow)
- DOM-IDEN-005 §VIII (Identity Binding)
- FEAT-CORE-000 (Feature Execution Constitutional Directive)

---

## II. Execution Context

### 1. Required Inputs

* `user_id`: The user created by FEAT-IDEN-001 (from session or context).
* `seat_id`: The seat claimed in FEAT-IDEN-001 (from session or context).
* `class_id`: The class context (from session or context).
* `credentials`:
    * `username`: Chosen username (generated by UI or entered by student).
    * `pin`: 4-6 digit PIN for login authentication.
    * `passphrase`: Passphrase for gating financial actions (separate from PIN).
* `idempotency_key`: Client-provided unique request ID for retry safety.

### 2. Resolved Context (MANDATORY)

Before mutation, the FEAT MUST resolve:
* The `User` record matching `user_id` in the `users` table.
* The `Seat` record matching `seat_id` in the `seats` table.
* Verify that `User.id == Seat.user_id` (seat is bound to this user).
* Verify that `Seat.class_id == class_id` (seat is in the correct class).

---

## III. Orchestration Logic

### A. Verification Phase (Read-Only)

#### Step 1: Validate User State
1. Query `User` record where `id = user_id`.
2. Verify that `pin_hash IS NULL` and `passphrase_hash IS NULL`.
   - This confirms the user is pre-provisioned but not yet activated.
3. Verify that `user_role = 'student'`.
4. **Failure Behavior**: Abort with `INVALID_USER_STATE` if user is already activated or not a student.

#### Step 2: Validate Seat State
1. Query `Seat` record where `id = seat_id`.
2. Verify that `user_id = user_id` (seat is bound to the target user).
3. Verify that `claimed_at IS NOT NULL` (seat was already claimed).
4. Verify that `role = 'student'`.
5. **Failure Behavior**: Abort with `INVALID_SEAT_STATE` if seat is not claimed or not bound to this user.

#### Step 3: Validate Username Uniqueness
1. Query `users` table where `username_lookup_hash = HASH(username)`.
2. **Failure Behavior**: If a row exists, abort with `USERNAME_TAKEN` (username already in use).

#### Step 4: Validate Credentials
1. **Username**:
   - Must be 3-32 characters.
   - Must contain only alphanumeric characters, dashes, underscores.
   - Must not be a reserved system word.
2. **PIN**:
   - Must be 4-6 digits.
   - Must not be all the same digit (e.g., "1111").
   - Must not be sequential (e.g., "1234").
3. **Passphrase**:
   - Must be 8+ characters.
   - Must contain at least one letter and one number.
   - Must not contain the username.
4. **Failure Behavior**: Return validation errors with specific failure reason.

---

### B. Mutation Phase (Atomic Transaction)

All mutations in this section **MUST** occur within a single database transaction.

#### Step 1: Hash Credentials

Perform credential hashing outside the transaction (one-time cost):
- `username_hash = HASH_STRONG(username)` (one-way hash for uniqueness checking and lookup)
- `username_lookup_hash = HASH_HMAC(username.lower(), secret)` (normalized for case-insensitive lookup)
- `pin_hash = HASH_PASSWORD(pin)` (bcrypt with salt + pepper)
- `passphrase_hash = HASH_PASSWORD(passphrase)` (bcrypt with salt + pepper)

#### Step 2: Activate User Credentials

Update the `User` record with credential hashes:
1. Set `username_hash = username_hash`
2. Set `username_lookup_hash = username_lookup_hash`
3. Set `pin_hash = pin_hash`
4. Set `passphrase_hash = passphrase_hash`

Per DOM-IDEN-002 §VI:
> "Student-specific fields: `pin_hash`, `passphrase_hash`"

#### Step 3: Finalize Seat State

Update the `Seat` record to mark setup complete:
1. Verify (but do not modify) `claimed_at` is not NULL.
2. No additional seat mutations needed; claiming already set all required fields.

#### Step 4: Clear Onboarding State (Session)

The route handler SHALL clear session state used during onboarding:
- Clear `onboarding_seat_ref`
- Clear `onboarding_user_ref`
- Clear `generated_username` (if used)
- Clear `theme_prompt` and `theme_slug` (if used)

**Note:** This is application-level housekeeping, not a database mutation.

#### Step 5: Context Establishment

Establish the authenticated session context:
1. Set `current_session_started_at = NOW()` on the User (per DOM-IDEN-002 §VII).
2. Set `current_session_expires_at = NOW() + SESSION_DURATION` (fixed window, does not slide).
3. Generate `current_session_nonce` (random token binding this session).

Per DOM-IDEN-002 §VII (Session Establishment):
> "`current_session_started_at` is written at sign-in."
> "`current_session_expires_at` is written once at sign-in (fixed window, does not slide forward on activity)."
> "`current_session_nonce` is regenerated at sign-in..."

#### Step 6: Audit Trace

Per FEAT-CORE-000 §III.4:

1. Call `DOM-OPS` to emit an `ACT-IDEN-002` audit event.
2. **Required fields**:
   - `feat_id`: "FEAT-IDEN-002"
   - `user_id`: The activated `user_id`
   - `seat_id`: The claimed `seat_id`
   - `class_id`: The classroom context
   - `idempotency_key`: The provided key
   - `outcome`: `"CREDENTIAL_ACTIVATED"` (only possible outcome)
   - `timestamp`: ISO 8601 UTC timestamp

**Note:** DO NOT log the actual username, PIN, or passphrase.

## IV. Invariants & Constraints

### 1. Credential Activation (MANDATORY)
Once this FEAT completes, the student can log in with their username and PIN (per DOM-IDEN-002 §VII).

### 2. Pre-Claim Requirement (MANDATORY)
This FEAT **SHALL ONLY** execute on a `User` that:
- Has no credentials (`pin_hash IS NULL`),
- Has a bound seat (`Seat.user_id == User.id`),
- Has a claimed seat (`Seat.claimed_at IS NOT NULL`).

### 3. Username Uniqueness (MANDATORY)
Per DOM-IDEN-002 §VI:
> "`pin_hash` and `passphrase_hash` SHALL be `NULL` for non-student users."

The username lookup hash SHALL ensure only one student can use a given username.

### 4. Single Activation (MANDATORY)
Once activated, credentials **SHALL NOT** be re-activated by this FEAT. Re-setting credentials requires account recovery (separate FEAT).

### 5. Atomic Transaction (MANDATORY)
All credential mutations SHALL occur in a single transaction. If any step fails, complete rollback occurs.

---

## V. Idempotency

**Mechanism:** The combination of `idempotency_key` and `user_id` acts as the idempotency lock.

**Behavior:**
- If a retry occurs with the same `idempotency_key`:
  - Check if `User.pin_hash IS NOT NULL` (credentials already activated).
  - If true, return success with the same outcome.
  - If false, re-attempt the full mutation (no duplicate state).
- Replayed requests with the same `idempotency_key` **SHALL NOT** create duplicate audit events.

**Client Responsibility:**
- Generate a stable `idempotency_key` (e.g., based on session or user context).
- Retry on transient errors with the same key.
- Server stores key on audit log to detect and skip replays.

---

## VI. Failure Scenarios

When the FEAT fails, the system SHALL:

1. **Rollback all mutations** atomically.
2. **Emit audit event** with outcome `FAILED` and error code.
3. **Return error response** to client.
4. **NOT advance the student** past the credential setup step.

**Failure Cases:**

| Scenario | Error Code | HTTP Status | Message |
|----------|-----------|-------------|---------|
| User already activated | `INVALID_USER_STATE` | 409 | "This account is already activated. Please log in." |
| Seat not claimed | `INVALID_SEAT_STATE` | 409 | "Invalid setup state. Please start over." |
| Username taken | `USERNAME_TAKEN` | 400 | "That username is already taken. Please choose another." |
| Username invalid | `INVALID_USERNAME` | 400 | "Username must be 3-32 characters, alphanumeric only." |
| PIN invalid | `INVALID_PIN` | 400 | "PIN must be 4-6 digits, not all the same or sequential." |
| Passphrase invalid | `INVALID_PASSPHRASE` | 400 | "Passphrase must be 8+ characters with letters and numbers." |
| User/seat mismatch | `CONTEXT_MISMATCH` | 400 | "Setup state mismatch. Please start over." |
| Database error | `INTERNAL_ERROR` | 500 | "An error occurred during setup. Please try again." |

## VIII. Integration with FEAT-IDEN-001

**FEAT-IDEN-002 is the second step of the student claim flow:**

```
Step 1: FEAT-IDEN-001 (Unauthenticated Seat Claim)
├─ Input: join_code, first_name, last_name
├─ Output: user_id (uncredentialed), seat_id
└─ User state: created but NOT authenticated

Step 2: FEAT-IDEN-002 (Credential Setup)
├─ Input: user_id, seat_id, username, pin, passphrase
├─ Output: authenticated session
└─ User state: credentials activated, ready to log in
```

Both FEATs **MUST** execute successfully for claim to complete.

---

## IX. Relationship to Account Recovery

**FEAT-IDEN-003** (Account Recovery) uses a similar credential-setting path but:
- Operates on an already-bound seat (`user_id IS NOT NULL`).
- Requires teacher-initiated reset code.
- Uses reset code for authorization (instead of claim credentials).
- Clears old credentials before setting new ones.

FEAT-IDEN-002 assumes the user is pre-provisioned and uncredentialed. Recovery is a separate FEAT.
